Standard test reports

Running an automated test is only the beginning.

Once you have hundreds or thousands of tests running in CI, you also want to know things like:

  • Which tests failed?
  • Which tests are flaky?
  • How long are they taking?
  • What code did they cover?
  • Are failures increasing over time?
  • Should this pull request be allowed to merge?
  • How do these results get into our test management system?

There is an entire ecosystem of tools built around answering those questions.

SpecBinder's approach is to use that ecosystem. It generates ordinary JUnit 5 tests, so your build can produce the same reports it produces for your other Java tests.

Your team can keep using the reporting tools it already knows.

Reports from your build tool​

SpecBinder generates ordinary JUnit 5 tests, as explained in Plain JUnit 5. Your build tool produces their test results just as it does for your other Java tests.

A scenario becomes a test method, a Rule becomes a nested class, and the feature becomes the test class:

Feature: Shopping cart

  Rule: Bulk discounts apply to large orders

    Scenario: Twelve units earn the bulk rate
      Given my cart contains 12 units at "5.00"
      Then the cart total should be "54.00"
@DisplayName("Feature: Shopping cart")
public abstract class ShoppingCartScenarios extends ShoppingCartFeature {

    @Nested
    @DisplayName("Rule: Bulk discounts apply to large orders")
    public class Rule_1 {

        @Test
        @DisplayName("Scenario: Twelve units earn the bulk rate")
        public void rule_1_scenario_1() {
            myCartContains$p1UnitsAt$p2(12, 5.00);
            theCartTotalShouldBe$p1(54.00);
        }
    }
}

There is nothing unusual for the build tool to notice. It is a JUnit 5 class.

Maven projects use Surefire for test results, or Failsafe for integration tests. Both write JUnit-compatible XML. Gradle's standard test task writes the same XML, and an HTML report alongside it.

Those result files are the starting point for the tools that follow.

Why JUnit-compatible results matter​

JUnit XML is something of an accidental standard in automated testing.

It isn't limited to JUnit anymore. Many CI servers, test analytics products, reporting tools and test management systems accept it.

That means SpecBinder scenarios can appear in the same infrastructure that already handles the rest of your Java tests.

For a tool that already accepts your build's JUnit XML, there is no SpecBinder-specific report format to teach it.

JaCoCo never reads the report at all: it attaches to the JVM while the tests run. The JSON report is optional, and it feeds tools that care about the specification rather than the tests, such as the SpecBinder IntelliJ plugin. Both are covered further down.

CI test reports​

Take a typical CI pipeline.

The build runs the tests and produces JUnit results. Your pipeline then publishes those results using its usual test-report integration.

Jenkins can consume JUnit XML and provide test histories, failure tracking and trends. GitLab can display JUnit test results directly in pipelines and merge requests. Azure Pipelines accepts JUnit as one of its standard test-result formats, and CircleCI can collect the XML reports generated by Gradle.

You still configure where the CI system should look for the files. Once published, results carry outcomes, durations and failure details into the same views your team uses for other tests.

Those durations help you find slow scenarios. When your CI system retains history and matches a test across runs, you can also investigate when failures began and whether they are becoming more frequent.

From the CI system's point of view, a SpecBinder scenario is a test. Which is exactly what we want.

Existing merge gates keep working​

Most teams eventually make automated tests part of their merge policy.

Run the test suite.

If something fails, fail the build.

If the build fails, don't merge.

Because SpecBinder scenarios participate in the normal JUnit execution process, the same mechanism applies to them. There isn't a second Gherkin execution status that needs to be translated back into the CI pipeline.

The CI server still gets its normal process result and its normal test reports.

Gherkin fits into the testing workflow your team already uses.

Flaky-test detection becomes available too​

A passing test today and a failing test tomorrow is often more interesting than either result on its own.

That is why modern test analytics tools retain test history and look for patterns across many executions.

Buildkite's Test Engine, for example, accepts JUnit XML results and provides tools to identify flaky tests, track reliability and investigate slow tests over time.

If your Gherkin scenarios are represented as ordinary JUnit tests, they can participate in this kind of analysis too.

A scenario that fails intermittently is no longer just:

"That Gherkin test occasionally goes red."

It can become a test with an execution history, reliability data and a measurable failure pattern.

That gives you evidence to investigate. It does not tell you why the scenario is unreliable, or remove the need to fix it.

Coverage tools don't need special treatment​

Code coverage is slightly different.

Tools such as JaCoCo don't learn about coverage from JUnit XML. They instrument the JVM while your tests execute and record which application code was exercised.

But the same SpecBinder design decision helps here too.

Because SpecBinder tests execute through the normal Java/JUnit toolchain, JaCoCo can run alongside them in exactly the same way it runs alongside other JUnit tests. Its Maven integration, for example, attaches the JaCoCo runtime agent to tests executed through Surefire or Failsafe.

There is no separate SpecBinder execution engine for the coverage tool to understand.

Your Gherkin scenarios simply contribute to your project's coverage.

Test management systems can consume the results​

The benefits don't stop at CI.

Many teams also push automated execution results into test management platforms.

TestRail, for example, supports importing JUnit XML and can map its test suites and test cases into TestRail entities and results. It provides a specific JUnit 5 integration built around this approach.

Again, SpecBinder doesn't need to build a TestRail integration.

The integration already exists at the JUnit layer.

That distinction is important.

You still configure the importer, provide access and decide how automated results map to test cases. What you avoid is building or maintaining a SpecBinder-specific integration for a job the existing JUnit integration already does.

When you need the steps inside a scenario​

Standard test reports tell you whether a scenario passed, how long it took and what failure was reported. A stack trace can help locate a failing assertion, but it is not a structured record of every Gherkin step.

Sometimes that is the detail you want: which steps passed, which one failed, and which were never reached.

For that, SpecBinder provides an optional JUnit 5 extension, dev.specbinder:execution-reporter. It writes a JSON report per feature, preserving the Gherkin hierarchy and recording step text, arguments, outcomes, timings and failure details.

It runs alongside the standard reports. Your CI system can keep consuming JUnit XML while tooling that needs the specification's detail uses the additional JSON.

See Execution reporter for setup and configuration.

What you still configure​

Using standard tooling reduces the number of custom integrations you need. There is still setup to do.

Your build must compile and discover the generated tests. Your CI pipeline must publish the report files. Coverage needs its normal configuration, and a test-management importer needs its connection and mapping settings.

These are familiar jobs if your team already runs Java tests. SpecBinder lets you reuse that knowledge for your Gherkin scenarios too.

Sometimes boring infrastructure is a feature​

There isn't much excitement in saying:

"Our Gherkin scenarios produce normal JUnit results."

But that's rather the point.

Infrastructure is often most useful when nothing special needs to happen.

Gherkin  ->  generated JUnit 5  ->  the reports your build already writes

Your SpecBinder scenarios can sit alongside your unit tests, integration tests and other JUnit tests. They run through the same build system, produce familiar results and feed the same downstream tooling.

SpecBinder adds Gherkin.

It doesn't ask you to replace everything that already works around it.

And sometimes the best integration is the one you don't have to build.
