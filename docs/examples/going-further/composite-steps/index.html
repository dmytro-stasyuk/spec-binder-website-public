Composite Steps

Write one business action in the spec — "the customer checks out" — and list the steps that carry it out right under it. The scenario reads at the level of the action, while the generated test still calls a method for each of those steps, in the order the spec lists them.

Source: examples/going-further/example-11 on GitHub.

What this demonstrates​

  • enableCompositeSteps = true turns a step followed by * steps into a composite step, and the * steps into its sub-steps
  • Sub-steps reading their composite step's quoted values — "<$p1>", "<$p2>"
  • A sub-step taking its composite step's whole data table — "<$dataTable>" — and one reading a single cell — "<$product[1]>"
  • A sub-step taking its composite step's doc string — "<$docString>"
  • Composite steps in a Background and in a Scenario Outline
  • A generated composite method overridden in the test class to check the action as a whole
  • The execution report showing each composite step with its sub-steps

Turn composite steps on​

Set enableCompositeSteps on the marker class. A bare @Gherkin2JUnit discovers Checkout.specb next to it by convention, and SpecBinderReporter writes the execution report.

CheckoutFeature.java
@Gherkin2JUnit
@Gherkin2JUnitOptions(enableCompositeSteps = true)
@ExtendWith(SpecBinderReporter.class)
public abstract class CheckoutFeature {
}

The option is off by default. With it off, a * step is an ordinary step of its own, run after the step above it.

Write a composite step​

A step directly followed by one or more * steps is a composite step, and the * steps are its sub-steps. Sub-steps refer to the composite step's values in double quotes: "<$p1>" is its first quoted value, "<$p2>" its second.

Checkout.specb (excerpt)
  Scenario: Buying one product
    Given the cart holds "2" of "Notebook"
    * search the catalogue for "<$p2>"
    * add "<$p1>" of the first result to the cart
    When the customer checks out
    * open the cart
    * confirm the delivery address
    * pay with the saved card
    Then the order total should be "9.00"

The scenario still reads as three steps — the cart holds two notebooks, the customer checks out, the total is 9.00 — and the sub-steps say how each one is done. In IntelliJ IDEA, the SpecBinder plugin opens the spec exactly that way: each composite step's sub-steps are folded away under it, so a scenario shows only its business actions until you unfold one. A composite step's own data table or doc string stays in view, and Fold composite steps on open under Settings → Tools → SpecBinder → Editor turns the folding off.

Two buttons on the spec's toolbar, right after the ones for scenarios, fold and unfold every composite step at once. Expand All Composite Steps (on the left below) shows the sub-steps of every composite step in the spec, and Collapse All Composite Steps folds them away again. Scenarios and other folds stay as they are, and both buttons work in the Execution Report pane too. They appear once Show toolbar buttons that expand and collapse all composite steps is ticked in the same Settings section, and each can be given a shortcut under SpecBinder in the Keymap.

Generated output​

Each composite step gets a composite method. It takes the step's values and a lambda holding the sub-steps' calls, and runs that lambda. Each sub-step gets an ordinary step method — the same one it would get written as a step of its own.

CheckoutScenarios.java (excerpt)
protected void theCartHolds$p1Of$p2(Integer p1, String p2,
        BiConsumer<Integer, String> subSteps) {
    subSteps.accept(p1, p2);
}

public abstract void searchTheCatalogueFor$p1(String p1);

public abstract void add$p1OfTheFirstResultToTheCart(Integer p1);

protected void theCustomerChecksOut(Runnable subSteps) {
    subSteps.run();
}

@Test
@DisplayName("Scenario: Buying one product")
public void scenario_1() {
    /*
     * Given the cart holds "2" of "Notebook"
     */
    theCartHolds$p1Of$p2(2, "Notebook", (p1, p2) -> {
        /*
         * * search the catalogue for "<$p2>"
         */
        searchTheCatalogueFor$p1(p2);
        /*
         * * add "<$p1>" of the first result to the cart
         */
        add$p1OfTheFirstResultToTheCart(p1);
    });
    // … the customer checks out, the order total …
}

A value keeps the type it has on the composite step: "2" is an Integer, so it reaches add "<$p1>" of the first result to the cart as an Integer too. A composite step without values, like the customer checks out, takes a Runnable.

Pass on a data table or a doc string​

A sub-step can refer to more than the composite step's quoted values:

Reference in a sub-stepPasses onGenerated argument
"<$p1>" … "<$p5>"the composite step's first to fifth quoted valuep1, p2, …
"<$product[1]>"the product cell of the first row of its data tabledataTable.get(0).product()
"<$dataTable>" at the end of the textits whole data tabledataTable
"<$docString>" at the end of the textits doc stringdocString

A reference can also sit inside other text, as in "CUST-<$p1>". When the data table has a single row, "<$product>" reads its cell without a row number.

A data table​

Checkout.specb (excerpt)
  Scenario: Buying products listed in a table
    Given the cart holds these products:
      | product  | quantity |
      | Notebook | 2        |
      | Pen      | 3        |
    * add the products to the cart: "<$dataTable>"
    * the first cart line should be for "<$product[1]>"

The composite method receives the table as dataTable. The first sub-step takes it as its own data table, and the second reads one cell of it:

CheckoutScenarios.java (excerpt)
theCartHoldsTheseProducts(
        List.of(
                new CartParam("Notebook", 2),
                new CartParam("Pen", 3)
        ), (dataTable) -> {
    addTheProductsToTheCart(dataTable);
    theFirstCartLineShouldBeFor$p1(dataTable.get(0).product());
});

The table is built with the row type of the sub-step that takes it, so the cart holds these products: and add the products to the cart: "<$dataTable>" share CartParam.

A doc string​

Checkout.specb (excerpt)
    And the order carries a gift note:
      """
      Happy birthday, Bob!
      """
    * open the gift options
    * write the gift note: "<$docString>"

The composite method receives the doc string as docString, and write the gift note: "<$docString>" takes it as its own:

CheckoutScenarios.java (excerpt)
theOrderCarriesAGiftNote("""
        Happy birthday, Bob!
        """, (docString) -> {
    openTheGiftOptions();
    writeTheGiftNote(docString);
});

In a Background and a Scenario Outline​

A composite step works wherever a step does. In the Background, "Alice" is signed in signs in before every scenario:

Checkout.specb (excerpt)
  Background:
    Given the shop sells:
      | product  | price |
      | Notebook | 4.50  |
      | Pen      | 1.20  |
      | Backpack | 25.00 |
    And "Alice" is signed in
    * open the sign-in page
    * sign in as "<$p1>"

In a Scenario Outline, Examples values in the composite step reach its sub-steps through the same references:

Checkout.specb (excerpt)
  Scenario Outline: A discount code takes its percentage off the order
    Given the cart holds "<quantity>" of "<product>"
    * search the catalogue for "<$p2>"
    * add "<$p1>" of the first result to the cart
    When the customer checks out with the discount code "<code>"
    * open the cart
    * apply the discount code "<$p1>"
    * confirm the delivery address
    * pay with the saved card
    Then the order total should be "<total>"

    Examples:
      | product  | quantity | code   | total |
      | Notebook | 2        | SAVE10 | 8.10  |
      | Backpack | 1        | BOGUS  | 25.00 |

The test method passes the row's values to the composite method, and the lambda hands them on:

CheckoutScenarios.java (excerpt)
public void scenario_4(String product, Integer quantity, String code, Double total) {
    theCartHolds$p1Of$p2(quantity, product, (p1, p2) -> {
        searchTheCatalogueFor$p1(p2);
        add$p1OfTheFirstResultToTheCart(p1);
    });
    // …
}

Implement the sub-steps​

CheckoutTest implements the regular steps and the sub-steps, and nothing else. A composite method already runs its sub-steps, so it never needs implementing:

CheckoutTest.java (excerpt)
public class CheckoutTest extends CheckoutScenarios {

    private final Shop shop = new Shop();
    private Shop.Order order;

    @Override
    public void searchTheCatalogueFor$p1(String text) {
        shop.search(text);
    }

    @Override
    public void add$p1OfTheFirstResultToTheCart(Integer quantity) {
        shop.addFirstResultToCart(quantity);
    }

    @Override
    public void payWithTheSavedCard() {
        order = shop.payWithSavedCard();
    }

    // … the other steps and sub-steps …
}

Shop is a tiny in-memory web shop that ships with the example. Most of its actions need a particular page to be open, so the sub-steps only work in the order the spec lists them.

Override a composite method​

A composite method is protected, so the test class can take it over. CheckoutTest overrides the one for the customer checks out to check the checkout as a whole, whichever sub-steps it is written with:

CheckoutTest.java (excerpt)
@Override
protected void theCustomerChecksOut(Runnable subSteps) {
    super.theCustomerChecksOut(subSteps);
    assertNotNull(order, "Checking out should place an order");
}

The class hierarchy​

CheckoutFeature.java          (marker — @Gherkin2JUnit, enableCompositeSteps = true, the reporter)
  └→ CheckoutScenarios.java   (generated, abstract — composite methods run their sub-steps)
      └→ CheckoutTest.java    (your concrete class — implements the steps and sub-steps)

Run it​

Run the example from the SpecBinder repository root with JDK 21.

./mvnw -pl examples/going-further/example-11 -am test

All five scenario executions should pass — three Scenarios and the Scenario Outline's two rows. Open target/generated-test-sources/test-annotations/ in the example module to see the generated class.

Execution report​

The run writes target/specbinder-reports/dev/specbinder/examples/goingfurther/compositesteps/CheckoutTest.json. A composite step is one entry in steps[], and its sub-steps sit in its subSteps[], each with its text as written in the spec, the values it ran with, its status and its timing:

CheckoutTest.json (excerpt)
{
  "methodName" : "theCartHolds$p1Of$p2",
  "text" : "Given the cart holds \"2\" of \"Notebook\"",
  "arguments" : [ { "type" : "simple", "value" : 2 }, { "type" : "simple", "value" : "Notebook" } ],
  "status" : "passed",
  "subSteps" : [ {
    "methodName" : "searchTheCatalogueFor$p1",
    "text" : "* search the catalogue for \"<$p2>\"",
    "arguments" : [ { "type" : "simple", "value" : "Notebook" } ],
    "status" : "passed"
  }, {
    "methodName" : "add$p1OfTheFirstResultToTheCart",
    "text" : "* add \"<$p1>\" of the first result to the cart",
    "arguments" : [ { "type" : "simple", "value" : 2 } ],
    "status" : "passed"
  } ]
}

When a sub-step fails, the error sits on that sub-step, its composite step fails, and the sub-steps and steps after it are reported as skipped.

What the build checks​

  • A reference that matches nothing fails the build, with an error listing the references the composite step offers — for example "<$p3>" under a step with two quoted values.
  • A composite step takes up to five values, a data table or doc string counting as one. Six or more fail the build.
  • A reference outside double quotes is plain text. In * sign in as <$p1>, the <$p1> is part of the step's text, not a reference. To write a literal <$ in a sub-step, write \<$.

Tooling support​

  • In the IntelliJ plugin, Cmd+Click on a composite step opens its composite method, or your override of it, and on a sub-step its own step method. References such as "<$p1>" get a colour of their own, and a composite step's sub-steps fold away under it, so a spec opens reading at the level of its composite steps.
  • The execution reporter records each sub-step under its composite step, as shown above.

See the enableCompositeSteps reference for the option itself.
